# Topic summaries

Summary generation consumes the topic tree and its source sentence ranges. Every node's sentences are split into contiguous runs, and each run is resolved on its own. Leaf runs are summarized from source text (in bounded chunks, merged, when a run is too large for one request). A parent run whose sentences all come from a single child reuses that child's run summary; a run that mixes several children — or includes the parent's own sentences — is generated from the original leaf checkpoint summaries plus any uncovered source text. Every ancestor uses those same original checkpoints, never the generated intermediate parent summaries. Complete, successful, non-overlapping checkpoint runs replace their source only when shorter; missing, empty, failed, ambiguous, or partially covered runs retain their source. Original short parent runs (at most 150 words and 1200 characters) are still returned verbatim, and oversized condensed inputs still use bounded chunking and merging.

Previously, mixed parent runs reread their aggregated subtree source. In a densely branching tree this could process approximately the article length at each internal level, though the root is skipped and single-child runs are reused. The new approach reduces repeated source input; savings depend on tree shape and leaf compression, and parent calls are still required for mixed runs. The quality tradeoff is explicit: facts omitted from a leaf summary are unavailable to its parents. Using the original leaves at every level avoids further loss from recursively compressing parent summaries, but does not recover those omitted facts. No fixed token or latency reduction is guaranteed.

Completed provider results are cached as durable `source_summary_units`, valid only while the record's content revision and input fingerprint still match, so retrying or skipping part of a run reuses the work already paid for. Successful summaries are written in both a leaf-oriented checkpoint and a view-oriented summary index. A provider or topic-level failure can leave the record in a reviewable state so the user can retry or skip the affected work without discarding completed summaries.
